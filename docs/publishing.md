# Approval-based Telegram publishing

Official API reviewed 2026-10-04: https://core.telegram.org/bots/api#sendvideo, https://core.telegram.org/bots/api#sendmessage and https://core.telegram.org/bots/api#responseparameters. This implementation supports plain-text POST and approved SHORT_VIDEO in Telegram channels. MP4 upload is multipart, bounded to 50,000,000 bytes; captions are limited conservatively to 1024 UTF-16 code units and text to 4096. No parse mode, paid broadcast, link preview or automatic social reply is enabled. Telegram's channel visibility and linked-discussion setting must match the plan; the adapter does not pretend to set per-message privacy or comments.

## Approval and scheduling

A verified OWNER/ADMIN/MANAGER explicitly approves the selected calendar revision, connection and future UTC timestamp. MANUAL plans cannot enqueue a task; AUTOPILOT remains unavailable. Server authorization, tenant/brand ownership, source video/script approval and original consent are checked in the transaction. The approved text (including hashtags), source, options, connection credential generation and schedule are snapshotted. Database triggers protect approval and publication evidence. A unique intent and unique calendar revision prevent duplicate approvals. Editing a frozen calendar entry is rejected. Cancel the pending task, edit/save a new revision and approve again.

`publishing_jobs` is the durable PUBLISH_CONTENT job/outbox. A dedicated BullMQ queue delivers due IDs; the database owns eligibility, attempt count and leases. Redis delivery can be lost or duplicated without authorizing a duplicate submission. SCHEDULED → PREPARING → SUBMITTING → PUBLISHED is audited. Safe preparation failures retry with bounded exponential delay, up to three attempts. A job more than 24 hours late fails instead of silently publishing stale content. Schedules are limited to the next 366 days. UI browsing uses 60-day calendar windows and the latest 100 publication tasks.

The worker rechecks the approver's role, exact plan revision, credential generation, video/source approval and consent immediately before submission. It inspects current channel rights and settings before downloading private media. A 120-second operation deadline and 180-second database lease bound preparation plus sending; Telegram requests are limited to 45 seconds. Credential replacement/disconnection cancels SCHEDULED/PREPARING jobs and fences their send marker. A request that has already crossed SUBMITTING cannot reliably be recalled; neither cancel nor consent revocation can undo an external request already in flight.

## Uncertain outcomes

Telegram does not document a send idempotency key. SUBMITTING is persisted before the one HTTP attempt. A validated successful Message is stored in `publications` atomically with PUBLISHED. A validated provider rejection fails the task. Timeouts, malformed responses, wrong destination, connection loss or a crashed SUBMITTING lease enter RECONCILIATION. Such jobs never automatically resend and cannot be canceled/reapproved as the same calendar material. A late acknowledgement with the original lease may still complete the task. Manual operator investigation/resolution is a remaining workflow; the UI explicitly reports this boundary and exposes no unsafe resend action.

Publication status means the saved acknowledgement at send time. The Bot API has no generic getMessage endpoint, so the application does not invent a live existence check. Later Telegram deletion is not detected. Removing a local video does not delete its Telegram publication. Analytics are not fabricated from a successful send.

## Configuration and verification

Set PUBLISHING_ENABLED=true, SOCIAL_PROVIDER=telegram and the credential vault variables on both web and persistent worker. Configure real private S3 for video. The disabled default reports CONFIGURATION_REQUIRED. Explicit development/test mock mode exercises the same database, queue, storage and processor; no Telegram message is sent. There is no AI/video credit charge for this free Bot API send. Other providers and paid broadcast capabilities need their own accounting and adapter review.

API: GET/POST `/api/organizations/:tenant/brands/:brand/publishing`, POST `/:id/cancel`. POST approval accepts calendarId, revision, connectionId and idempotencyKey. Only safe summaries are returned; snapshots' private storage keys, credentials and remote metadata remain server-side. Existing Origin, auth and mutation throttling apply. Tests cover manager/tenant checks, immutable approval, concurrency, deadlines, cancel fences, remote rejection/uncertainty and late acknowledgement. Browser verification includes review → scheduled worker delivery → saved status using the explicit mock provider.

Remaining full-product scope includes additional publishing platforms, operator reconciliation tooling, webhook ingestion, analytics, privacy retention/redaction policies, notifications and deployment. Immutable approval/publication evidence currently has no user-facing retention or redaction workflow; it must be designed before the full Privacy Center is considered complete.
