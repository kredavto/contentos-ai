# Agency client portfolio

The Clients page groups separate customer organizations under an agency organization. It does not flatten tenants or inherit access. Brands, team membership, usage ledger, subscriptions, content and provider connections remain owned by each customer organization. Agency administrators must explicitly invite colleagues to the customer team before they can see or operate it. This release does not pool billing across clients or infer a paid entitlement from an AGENCY plan label.

The deployment must enable `AGENCY_MODE_ENABLED=true` (default false). The agency OWNER then explicitly enables tenant feature `agency_mode`, using an optimistic integer revision. Disabling the mode hides the portfolio and blocks its mutations while leaving client organizations and their direct access intact. Other named feature flags have a validated storage namespace but retain their existing runtime gates until individually wired; this table is not an implicit override of publishing or consent controls.

OWNER and ADMIN can create a client organization or link an existing one. Linking requires current verified ownership of the target organization; linking the agency to itself is rejected. Creation atomically inserts the client organization, its first workspace, the creator's OWNER membership, the portfolio relationship and audit events. A stable UUID request key is bound to actor and normalized intent. Concurrent retries return the same client, including its current archived state, and recheck target membership. No email is sent and no trial credits or subscription are automatically granted.

OWNER/ADMIN/MANAGER can read the portfolio, but the query only returns client organizations where that same user still has direct membership. Knowing a relationship ID never authorizes access to client data. Loss of membership immediately hides the client and blocks replay disclosure. Disabling an account blocks all portfolio access; writes also require verified email.

Archiving changes only the portfolio relationship. Restoring requires ownership in the target organization. A UUID revision prevents stale state changes. An immutable-identity database trigger protects actor, client tenant, request key/hash and creation time. All mode, create/link, archive and restore actions are audited without content or credentials. There is an operational maximum of 200 relationships per agency, including archived relationships, to bound list and create operations; this is not a price or paid-plan promise.

Migration 0034 adds `feature_flags` and `agency_clients`. Both have UUID primary keys, foreign keys and uniqueness/validity constraints. The service validates strict request shapes, UUIDs and timezones; common BFF authentication, exact-Origin checks, mutation throttling and body limits apply.

PostgreSQL tests cover opt-in and deployment gating, concurrency, idempotent intent binding, direct membership isolation, foreign linking, immutable identity, archival persistence, revision conflicts, membership loss, disabled accounts and email verification. Browser verification covers owner activation, client creation, CSRF rejection, archiving/restoration and preserved client access after mode is disabled.
