# Social connections and credential vault

The first connection adapter uses official [Telegram Bot API](https://core.telegram.org/bots/api#getme) read methods: getMe, getChat and getChatMember (checked 2026-10-04). It accepts channels only and requires administrator status plus can_post_messages for ACTIVE. Missing posting rights produce LIMITED. Connection inspection does not send messages, alter permissions or leave the channel. Requests are bounded, redirects forbidden and responses validated. Logs contain method, correlation, timing and status; never a credential-bearing URL or raw error body.

The verified OWNER/ADMIN/MANAGER role is required before external inspection. Provider responses are rechecked under a tenant lock before commit. Connection creation uses an intent UUID and payload hash; duplicate channel mappings are rejected. Existing rows are reconnected explicitly with a new token for the same channel. Optimistic revisions fence races with disconnect or credential replacement. Credential version increments on replacement/disconnect, enabling publishing jobs to bind to a specific credential generation. Read-only refresh and encryption rewrap do not increment credential version.

The vault uses AES-256-GCM with fresh random 96-bit nonces and 128-bit authentication tags. Associated data binds tenant, brand, connection and provider. Envelopes carry a key ID; a keyring permits old-key decryption while new writes use the active key. The manager-authorized rewrap endpoint decrypts and re-encrypts server-side and audits the key ID only. Test coverage includes tampering, cross-tenant/brand/connection/provider substitution and key rotation.

Routes are beneath `/api/organizations/:tenantId/brands/:brandId/social`: GET/POST list/connect and POST `/:id/refresh`, `reconnect`, `disconnect`, `rewrap`. Revision is required for existing records. List responses contain display metadata/status only, never ciphertext, token, input hash or provider reference. Disconnect clears the stored credential; it does not revoke the Telegram token globally or remove the bot from the channel. Access to an old HTTP operation cannot restore a disconnected row.

Mock mode is explicit and development/test-only. Production needs independently generated encryption keys and an actual bot credential. No live Telegram call or message was sent during implementation. The connection layer is implemented; the publishing scheduler, immutable approval snapshot and unknown-send reconciliation remain the next required workflow.
