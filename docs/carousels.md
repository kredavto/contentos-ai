# Carousel Studio

The Carousel tab generates 2–10 editable text slides through the existing provider-independent structured LLM workflow. Brand Brain supplies context; every output is strictly validated. GENERATE_CAROUSEL reserves 4 AI credits from the database policy, captures on success and releases on terminal failure. Durable jobs, actor-bound idempotency and approval notifications use the existing worker pipeline.

Each carousel has immutable numbered JSON versions containing slides, caption, hashtags, internal fact-check notes and a design preset. Editing creates a version and clears approval. Optimistic version checks prevent overwriting concurrent edits. Writers and approvers have distinct permissions; viewers can read history and export approved slides. Tenant composite foreign keys and database history triggers provide defense in depth.

The browser renders actual PNG slides at 1080×1080 or 1080×1350 with selectable colors and sans/serif typography. Text wraps and shrinks within bounded regions; excessive text reports an error. Rendering uses local Canvas2D, with no remote fonts, image fetches, HTML or SVG. Fonts can vary between devices. Downloads require the currently selected saved version to be approved and unchanged. PNGs download individually or together in a browser-generated ZIP and are not persisted as media assets.

An approved carousel can prefill an independent CAROUSEL calendar draft with its caption and hashtags. Internal title/notes are excluded from copied publication text. This does not enqueue publishing or attach files: the user downloads and attaches slides during manual publication. Current publishing adapters do not send carousel albums. AI illustrations, server-side media storage, album publishing and permanent carousel deletion remain separate work. Reversible archival is available as described below.

Migration 0045 adds carousels and carousel_versions plus the usage policy and immutable-history trigger. No new provider credentials are required.

## Archive and restore (2026-10-14)

Writers can move a saved carousel to the archive and restore it. Active and archived lists each return up to 100 entries independently; archived records cannot push active records out of the list. Readers can inspect archived content and its immutable version history. The UI prevents editing, approval, export and calendar-copy creation for an archived selection; restoration requires fresh approval. Already downloaded PNGs and previously copied calendar drafts are independent copies and cannot be recalled by archiving. This is reversible organization, not permanent deletion or account erasure.

Migration 0057 adds `archived_at` and `lifecycle_revision`, defaulting old records to active at revision zero. A database constraint forbids approval on archived rows. Archive/restore uses `PUT /carousels/{id}/archive` with `{revision, lifecycleRevision, archived}`; the route applies the shared Origin check, authentication and mutation throttle. The repository requires a current writer, locks the tenant and carousel, verifies tenant/brand scope and both revisions, then clears approval, marks the source content item READY, increments its revision and writes a payload-free audit event containing only revision metadata. Versions and ledger entries are unchanged.

Editing/approval now accepts `lifecycleRevision` from the overview. An omitted value defaults to zero for old never-archived clients; once archival changes state, stale clients fail with CONFLICT even after restoration to the same content version. Concurrent edit/archive operations serialize, so a stale operation cannot overwrite the winner. Repeating the immediately completed archive/restore intent returns the current state without another audit event; older intents cannot replay across a later archive/restore cycle. Deploy the new API/web code together before exposing archival controls.

## Complete ZIP export (2026-10-15)

An approved, unchanged, active carousel can be downloaded as one ZIP containing `slide-01.png` through `slide-10.png` (only the actual number of slides) and UTF-8 `caption.txt` with the publication caption and hashtags. Names are generated internally; the title cannot introduce paths. Internal title and fact-check notes are excluded. Each PNG uses the existing Canvas2D renderer and saved design: 1080x1080 or 1080x1350. The ZIP preserves slide order. PNG export remains available separately; neither path spends credits or creates a publishing job.

The UI checks current membership, approval, content version and lifecycle revision through `GET /carousels/{id}/export?revision=...&lifecycleRevision=...` before rendering and again immediately before offering the download. Responses are no-store and contain only revision metadata. Archived/unapproved/stale versions are rejected; viewers can export an approved current version. Content changes, a different selection, lost eligibility, leaving the component or explicit cancellation abort the pending client operation. The new checks apply to individual PNG export too. Already downloaded or cached content cannot be recalled, and a browser-side check is not a DRM boundary.

Slides render sequentially into a temporary canvas, which is released after each file. The content is validated and copied once for a stable export snapshot. Progress is shown, and any render/authentication failure discards the pending archive rather than downloading a partial file. Each PNG is limited to 10 MiB, and the complete archive to 64 MiB. File naming is fixed, PNG output is validated, and only final bounded bytes reach the download link. Object URLs are revoked after use.

The ZIP implementation uses pinned fflate 0.8.3, loaded on demand, with stored entries (`level: 0`) because PNGs are already compressed. This follows the [maintainer's ZIP usage guidance](https://github.com/101arrowz/fflate#usage). There are no runtime CDN requests, compression worker scripts, extra remote fonts or provider calls. Server-side slide persistence and automatic album publishing remain outstanding; no database migration is needed for this slice.


## Complete version history (2026-10-15)

The studio loads immutable history in descending pages of 20 versions through `GET /carousels/{id}/history`, with an optional exclusive `before` version cursor. `items` contains the page and `nextBefore` is null at the beginning of history. A bounded 21-row read determines whether another page exists; the existing unique carousel/version index supports the lookup. Strict query validation rejects zero, fractions, out-of-range PostgreSQL integers and unknown parameters. Every page checks the current account, tenant membership and brand/carousel scope, including for archived content; responses are no-store. The older history endpoint remains compatible with its existing 100-row response.

Readers can expand a historical version to inspect all slide headings/text, caption, hashtags, notes and format. “Загрузить ранние версии” reaches versions older than the former 100-version ceiling. Failed requests retain the loaded rows and cursor for retry. Selecting another carousel, switching archive mode or saving clears the local history. Fetching the first page again refreshes the list; newly appended versions do not shift subsequent pages or introduce duplicates while traversing older versions. This is an immutable-history cursor, not a live snapshot of later edits.

Writers can take a loaded historical version as a local draft, then explicitly save it as the next numbered version. Historical rows remain unchanged, existing approval is cleared and export requires fresh approval. Read-only users and archived selections cannot take history as an editable draft. No credits, provider calls or database migration are required. The carousel list itself still shows the latest 100 records in each archive state; this slice removes the version-history limit, not that separate list limit.
