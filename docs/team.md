# Team access

Verified owners and administrators can open `/team?organization=<uuid>`. Owners may assign ADMIN, MANAGER, EDITOR, CLIENT_APPROVER or VIEWER; administrators may manage only the latter four roles. No generic role change or removal can target an OWNER. Transferring ownership explicitly promotes an existing verified, enabled member and demotes the acting owner to ADMIN in one tenant-locked transaction. The target and actor membership revisions must match the displayed state. This does not transfer historical payment consent; recurring billing continues to require its original consenting user's current owner authority.

Membership revisions are random UUIDs, replaced on every role change and created afresh on joining. A stale request cannot alter a later membership for the same user. Tenant locks serialize changes, transfers and invitation acceptance. Repository authorization always rechecks enabled users, verified email and current membership.

Invitations expire after seven days and target one normalized email. The manager obtains a manually shareable link; this feature does not automatically send mail. The token is carried in the URL fragment, hashed in the database, and encrypted separately for safe idempotent response recovery. Encryption AAD binds tenant and invitation IDs. Reusing an intent key with another email/role/issuer is rejected. There can be at most 100 active pending invitations per organization.

The recipient signs in or registers in another tab, verifies the invited email, then explicitly accepts. Acceptance rechecks the issuer's current authority, expiry, revocation and the recipient's verified identity. It never changes an existing member's role. Accepted-link replay is safe for a current member, but cannot restore a removed membership. Removing/demoting an issuer permanently revokes invitations they can no longer grant, so rejoining cannot reactivate old links. Accepted/revoked invitation envelopes are erased and terminal records cannot be rewritten. Team reads expose neither hashes nor encrypted tokens. Audit records omit email addresses and bearer tokens.

Migration 0032 adds `team_invitations` and membership revisions. Apply it before deploying this UI/API. The invitation vault uses the same configured versioned keyring as other encrypted credentials; absence disables invitation creation. Browser mutations retain the application's Origin checks and per-user rate limits.
