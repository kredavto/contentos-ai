# Batch notification read state

The inbox can mark up to 50 loaded unread notifications per explicit click. The button shows the exact batch size; after loading more pages, additional batches can be marked. New events and unloaded pages are not included implicitly. Individual read actions remain available. Failed requests keep the unread badges and allow retry; successful requests apply only the IDs/timestamps returned by the server and use its unread count. Refresh obtains newer events. Counts are a snapshot, not a live subscription.

`POST /organizations/{tenantId}/notifications/read-batch` accepts only `{ids: UUID[]}`, with 1–50 distinct IDs. Shared authentication, exact-Origin protection, JSON limits and mutation throttling apply. The service validates input before calling the repository. Every requested row must belong to the current user and tenant and remain visible to the current role; disabled accounts and revoked membership are rejected. A mixed authorized/unauthorized batch fails with the same safe NOT_FOUND response and changes nothing.

The transaction locks requested visible rows in UUID order, checks completeness, and then updates read_at with COALESCE so concurrent or repeated requests preserve the first read timestamp. The current membership stays locked for the transaction. The response contains only the affected IDs/read timestamps and the unread count for the recipient's current audience. There are no provider calls, email sends, ledger operations or new migrations. Existing single-item reads and pagination remain compatible.

## Unread inbox filter

The inbox offers All (the default) and Unread views. `GET /organizations/{tenantId}/notifications` accepts `status=ALL|UNREAD` and the existing optional UUID cursor; unknown fields and unsupported status values are rejected. Filtering happens in PostgreSQL before the 50-row limit, so unread events behind read pages remain reachable. The unread count always represents all currently visible unread events, independently of the page.

Cursor validation uses current tenant, recipient and role visibility, but does not require the cursor itself to remain unread. Its immutable creation time and ID continue to anchor pagination after a single or batch read. Newer events are available through Refresh; pagination does not shift backward to include them. Removing loaded cards after a successful read preserves the cursor and offers the next page even when the current page is empty. Failed reads or page loads preserve the current list/cursor for retry. Switching filters resets local results and pagination; pending requests disable filter changes, and the keyed view prevents stale requests from replacing another view. The filter resets to All after a page reload. No new migration or provider is required.
