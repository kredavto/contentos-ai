# BYOK credential storage foundation

Migration 0076 adds a brand-scoped provider-key store for the HeyGen/OpenAI providers named in specification §100. This is an internal foundation, not a finished BYOK integration: there is no management HTTP route or form yet, no provider verification, and existing generation/catalog workers still use their current configuration. Private voices and voice cloning remain unimplemented. ACTIVE means a locally available stored credential, not a verified provider connection.

The core service validates provider, printable ASCII key length (20–4096), scope UUIDs and expected revision. It authorizes the current verified organization owner and requires an active paid EXPERT or AGENCY term according to PostgreSQL time. Future terms and other plans do not qualify. Authorization and entitlement are rechecked under the tenant lock before commit. Listing metadata and revoking a key do not require an active paid term, so expiry cannot prevent removal of an existing secret.

Keys use AES-256-GCM through the existing versioned vault. A dedicated PROVIDER_KEY associated-data purpose binds ciphertext to tenant, brand, connection UUID and provider. Ciphertexts cannot be substituted into social credentials or another provider/brand/tenant. Keyring rotation can decrypt older envelopes and rewrap them using the active encryption key. Persistent ciphertext updates must advance the connection revision; future consumers must treat a changed revision as requiring a fresh authorized binding.

The owner-facing projection returns only ID, provider, mask, state, revision and update time. The mask contains eight bullets plus the last four characters, as requested in the specification. Neither plaintext nor ciphertext is returned by the management service. Audit metadata contains provider/brand identifiers only. Stored identity is immutable and revisions must advance. Revocation clears the ciphertext. Current masking metadata remains so the owner can identify the revoked connection.

Internal job resolution rechecks the authenticated requesting user’s verified membership and generation permission, exact tenant/brand/connection/revision, active credential state and current plan entitlement. It intentionally returns ciphertext only to trusted worker code. Future worker consumers must pass the persisted requesting user, decrypt with the bound scope, and obtain a provider adapter through the provider layer; this repository is not an HTTP API. Replacing/revoking a key invalidates old revision references. No fallback to a shared provider account is permitted for private assets.

Remaining work includes current provider API validation, management routes/forms, explicit connection binding throughout avatar/voice/video jobs, private voice consent and lifecycle, provider-specific LLM routing, operational handling of revoked credentials for already-submitted remote operations, account export/erasure handling before exposing management, and live acceptance. No user key has been requested or stored and no paid/provider operation was performed by this slice.
