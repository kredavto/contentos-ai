# BYOK credential storage foundation

Migration 0076 adds a brand-scoped provider-key store for the HeyGen/OpenAI providers named in specification §100. This is a partial BYOK integration: owners can manage encrypted keys, and the public voice catalog can explicitly bind a stored HeyGen key. Avatar API/worker execution supports an explicit immutable key revision; video API/worker execution inherits that same binding. An explicit read-only key authentication check is available; it does not establish account-wide generation capabilities. Private voices and voice cloning remain unimplemented. ACTIVE means a locally available stored credential, not a verified provider connection.

The core service validates provider, printable ASCII key length (20–4096), scope UUIDs and expected revision. It authorizes the current verified organization owner and requires an active paid EXPERT or AGENCY term according to PostgreSQL time. Future terms and other plans do not qualify. Authorization and entitlement are rechecked under the tenant lock before commit. Listing metadata and revoking a key do not require an active paid term, so expiry cannot prevent removal of an existing secret.

Keys use AES-256-GCM through the existing versioned vault. A dedicated PROVIDER_KEY associated-data purpose binds ciphertext to tenant, brand, connection UUID and provider. Ciphertexts cannot be substituted into social credentials or another provider/brand/tenant. Keyring rotation can decrypt older envelopes and rewrap them using the active encryption key. Persistent ciphertext updates must advance the connection revision; future consumers must treat a changed revision as requiring a fresh authorized binding.

The owner-facing projection returns only ID, provider, mask, state, revision and update time. The mask contains eight bullets plus the last four characters, as requested in the specification. Neither plaintext nor ciphertext is returned by the management service. Audit metadata contains provider/brand identifiers only. Stored identity is immutable and revisions must advance. Revocation clears the ciphertext. Current masking metadata remains so the owner can identify the revoked connection.

Internal job resolution rechecks the authenticated requesting user’s verified membership and generation permission, exact tenant/brand/connection/revision, active credential state and current plan entitlement. It intentionally returns ciphertext only to trusted server/worker code. Future worker consumers must pass the persisted requesting user, decrypt with the bound scope, and obtain a provider adapter through the provider layer; ciphertext is never part of the HTTP response. Replacing/revoking a key invalidates old revision references. No fallback to a shared provider account is permitted for private assets.

Remaining work includes current provider API validation, creation UI and safe connection rebinding, private voice consent and lifecycle, provider-specific LLM routing, operational handling of revoked credentials for already-submitted remote operations, full account-erasure orchestration, and live acceptance. Development acceptance uses synthetic fixture keys; no real user key or paid provider operation was used.

Account export now includes `providerKeyHistory`: only connection ID, provider and original creation time for rows created by the requesting account, even after membership ends. It excludes tenant/brand identifiers, current status/revision, key mask, ciphertext and later replacement metadata. Migration 0077 indexes this bounded creator-history query. This evidence is not a backup of provider credentials. Account deletion remains request intake only; the future erasure workflow must resolve shared organization ownership, revoke/clear affected credentials with revision fencing, reconcile submitted provider operations and handle retained creator references before pseudonymizing/deleting the account. A deletion request does not revoke an organization’s key automatically.

## Public voice catalog consumer

The existing authenticated brand voice refresh endpoint accepts an optional strict `connection: {id, revision}` alongside `cursor`. When present, it resolves that exact active brand/tenant key for the verified requester and current Expert/Agency term, decrypts the bound vault envelope and creates a request-scoped HeyGen adapter. Only HeyGen is accepted. It never falls back to the platform key when the reference is invalid, revoked, expired, foreign or encrypted under unavailable configuration. No credential is accepted in the refresh payload or returned to the caller. Existing Origin/mutation controls and tenant catalog rate limits still apply.

The adapter uses the existing public catalog contract only; no private voice endpoint or paid generation is called. Before saving the page, the repository locks the tenant and repeats membership, entitlement, exact key revision/state/provider checks in the same transaction as catalog writes. Replacement/revocation committed during the network read causes the response to be discarded. This cannot retract an HTTP read already submitted before revocation. Public catalog records remain reusable public assets; private assets will require separate provenance and consent.

Omitting `connection` retains the existing configured public catalog behavior. The owner management panel supplies the stored reference when explicitly loading through the brand key. The existing voice overview configuration indicator still describes the platform connection. Avatar/video API and worker binding is described below; private voice lifecycle remains incomplete. Integration tests inject catalog adapters and exercise a real disposable database; they do not validate live provider credentials.

## Owner management

GET/PUT `organizations/:tenant/brands/:brand/provider-keys` and POST `.../provider-keys/:id/revoke` use the existing authenticated BFF, strict service schemas, Origin checks, global per-user mutation budget and no-store responses. GET returns only masked metadata plus encryption-configuration readiness. Save requires a current verified owner and paid entitlement; list/revoke remain available after plan expiry. Replacement/revocation use expected revisions, so stale tabs must explicitly reload. Missing vault configuration prevents saving but does not prevent revocation.

The owner-only avatar-studio panel manages HeyGen, uses a password field with autocomplete disabled, clears its value immediately on submission and never persists it to browser storage. Saving reports encrypted storage, not provider verification. The explicit catalog action sends only ID/revision and supports subsequent pages. Ordinary editors do not receive management metadata. Their existing public catalog controls remain unchanged. API storage supports both configured provider enum values; OpenAI has no UI or execution consumer yet.

Revocation clears ciphertext locally and advances the revision; it does not revoke the external provider account key or retract an already submitted request. The interface explains this and the still-incomplete account-deletion workflow. A user can remove the stored secret through revocation while retaining masked connection/audit evidence; full account erasure still needs organization ownership resolution, remote reconciliation and retained-reference handling.

## Explicit key check

POST `.../provider-keys/:id/verify` accepts only the expected revision. It authorizes a current verified owner and active Expert/Agency term, resolves/decrypts the exact brand key, and calls the documented HeyGen `GET /v3/api_keys/self`. The provider adapter validates a nonempty key ID and active status, discards all external metadata and returns no identity/billing data. The service returns only `{accepted:true}` after rechecking owner, entitlement and exact active revision under the tenant lock. A key changed or revoked during the request cannot produce a successful check audit.

The key-check budget is ten requests per tenant/minute in addition to the existing authenticated mutation throttle. Timeouts and safe provider errors remain in force; no generation or other paid mutation is submitted. Checks do not change credential revisions or persist a misleading permanent VERIFIED state. The UI explicitly says that generation permission and balance were not checked. A successful check is momentary evidence of acceptance, not a guarantee that every future operation is authorized. Browser acceptance intercepts this endpoint; adapter contracts and database races are tested independently with synthetic fixtures.

Official contract verified 2026-10-23: https://developers.heygen.com/reference/get-current-api-key. The current user endpoint exposes a username but has not established an immutable account/resource-scope binding for BYOK generation. The avatar worker now binds an exact key revision instead of inferring account identity. Safe rebinding/rotation remains outstanding; video jobs now inherit the immutable avatar reference. Existing bounded mutation replay remains unchanged: https://developers.heygen.com/reference/create-avatar documents 24-hour replay; the current worker limit is 23 hours.

## Avatar job binding (API/worker slice)

Avatar creation accepts an optional `connection: {id, revision}` through its existing strict request schema. Migration 0078 adds nullable key ID/revision fields to avatars, an immutable binding trigger and a composite tenant/brand/key/provider foreign key. Existing avatars remain platform-bound with null fields. New BYOK requests require current generation permission, paid entitlement, exact active key, current subject consent and source media before the normal ledger reservation/outbox transaction. The job input snapshots the same binding; adding a look must match the parent binding.

The web/worker are wired with the credential vault. A request-scoped HeyGen avatar adapter is built from the exact bound key, without requiring a shared HeyGen connection or falling back to one. Prepare rechecks the key before submission; completion checks it again before capture. Replacement/revocation before submission fails without a provider call and releases the reservation. After a remote reference exists, unavailable credentials/entitlement pause into reconciliation and retain the reservation. Late references remain retained for cleanup. The provider's documented bounded same-key retry behavior is unchanged.

Deletion keeps the original binding and may execute after plan expiry because deletion was already authorized. It still requires the same active key revision; it never uses a replacement key or the platform account. Revoked/replaced credentials leave remote deletion pending. The current implementation does not offer automatic key rebinding/restoration; provider-side investigation/cleanup is needed when that original credential is unavailable. This operational limitation must be resolved for complete BYOK lifecycle support.

This slice exposes the binding at the API and worker layers, not a new avatar-creation selector in the UI. Video API/worker binding is now implemented as described below; the UI creation selector remains pending. Existing public catalog and owner key management remain unchanged. Deploy migration 0078 and matching workers before enabling BYOK avatar submissions; older workers cannot interpret the new job input. No live generation or account credential was used in acceptance.

## Video job binding (API/worker slice)

Migration 0079 adds immutable tenant/brand/provider/look/key/revision binding and a composite key foreign key on video projects. Video creation derives the exact key reference from its authorized ready avatar; callers cannot supply an unrelated key. It requires the current revision, entitlement, consent and verified requester before reserving video seconds. The job snapshots the same binding; all worker lookups check it against the project, and source validation checks the project against the avatar. Old platform projects retain null fields.

The worker resolves/decrypts that key for a request-scoped HeyGen video adapter, with no platform fallback. Preparation and completion recheck entitlement/revision; key loss before submission fails/refunds, while an accepted remote operation with unavailable credentials pauses into reconciliation and retains its reservation. The original request identity and bounded provider replay behavior remain unchanged. Captions and local media processing retain their existing configuration; BYOK applies to HeyGen video generation.

Cleanup uses the original revision independently of paid-term expiry, then removes private stored media only after remote deletion succeeds. Unavailable/replaced credentials leave deletion pending, with no account substitution. Safe rebinding/provider-side reconciliation is still outstanding. Already completed local media keeps the existing consent and authorization checks without requiring HeyGen credentials for a download.

Deploy migration 0079 and matching web/worker versions together before accepting bound video jobs. This is not a live provider acceptance result or a finished UI workflow; the avatar creation selector and complete key-rotation lifecycle remain pending.
