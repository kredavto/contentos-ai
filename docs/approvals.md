# Assigned script review

An author with the current generate permission can request review of an unapproved saved script version by a verified OWNER/ADMIN/MANAGER/CLIENT_APPROVER in the same organization. Request identities are actor-bound and idempotent. Only one pending request per script is allowed. An old pending request must be cancelled before another is created. The review inbox includes requests created by or assigned to the current user; organization managers can inspect all requests. Reviewer choices expose names and roles, not email addresses.

Only the named assignee with current approve permission can approve, reject or request changes. A request author or current manager can cancel. Rejection and change requests require a reason. An approval atomically applies the existing script approval operation and records the request decision; it does not generate video or publish anything. A changed or independently approved script cannot be approved through a stale request. Retry of an identical terminal decision returns its stored result; different decisions conflict. The exact reviewed script version remains visible, and terminal decisions/request identities cannot be changed or deleted. Audit events contain identifiers and version, not comment or script text.

Migration 0066 adds approval_requests with tenant/version foreign keys, pending-request uniqueness, validity checks and database evidence guards. HTTP mutations use existing authentication, Origin and shared rate limiting. A single in-app notification for the assignee is inserted atomically with the request and links to the approval inbox. Email delivery is not part of this slice. The request form appears only for a saved, unchanged script draft. The inbox is a separate authenticated organization page with bounded cursor pagination.

Scope: SCRIPT only. Addressed requests for posts, carousels, images and video; client portal filtering; and broader approval policy are remaining work. Existing direct role-based approval remains available; assigning a request does not silently introduce an exclusive approval policy. No external integration or SMTP is required for the current workflow.
