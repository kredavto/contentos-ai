# Assigned material review

Authors with current generate permission can request review of an unapproved saved SCRIPT, POST or CAROUSEL version by a verified OWNER/ADMIN/MANAGER/CLIENT_APPROVER in the same organization. Request identities are actor-bound and idempotent. Only one pending request per material is allowed. An old pending request must be cancelled before another is created. The inbox includes requests created by or assigned to the current user; organization managers can inspect all requests. Reviewer choices expose names and roles, not email addresses.

Only the named assignee with current approve permission can approve, reject or request changes. An author or current manager can cancel. Rejection and change requests require a reason. Approval atomically applies the existing material transition and records the decision; it does not generate video or publish anything. A changed or independently approved material cannot be approved through a stale request. Retry of an identical terminal decision returns the stored result; different decisions conflict. Exact reviewed content remains visible, and terminal decisions/request identities cannot be changed or deleted. Audits contain identifiers and version, not comment or material text.

Migration 0066 introduced SCRIPT requests. Additive migration 0067 adds explicit POST/CAROUSEL targets and a captured carousel lifecycle revision. Exactly one target is allowed. Tenant/entity/version foreign keys and the identity trigger prevent cross-tenant or cross-brand references. Existing script request input/hash normalization is unchanged. Archiving and restoring a carousel invalidates the old request even if content version is unchanged. Authors cancel and submit the current lifecycle explicitly; archived carousels cannot be submitted or approved.

HTTP mutations use existing authentication, Origin validation and shared rate limiting. The form appears only for saved unchanged content. The inbox uses bounded cursor pagination and rechecks current membership. One in-app notification is inserted atomically with the request and links to the inbox. Posts display the requested body and hashtags. Carousels use the existing canvas renderer for requested slide artwork and show every slide's text, caption and hashtags. Rendering errors are visible.

Validation: workspace/test-source TypeScript, ESLint, production build, 582 tests across 84 files, and two Chrome scenarios covering scripts plus post/carousel request → exact-version review → actual database approval. Tests cover duplicate/concurrent decisions, stale edits, carousel archive/restore, foreign tenant/brand and unassigned actor denial, immutable receipts, request notifications, no-store and internal-field exclusion. Mobile layout was checked at 390px and the carousel screenshot inspected. Disposable verification cleaned its resources.

Remaining: image/video requests, email delivery, broader client portal and approval policy. Existing direct role-based approval remains available; assigning a request does not silently introduce an exclusive approval policy. No external provider or SMTP is required for these workflows. Production infrastructure and full-platform readiness remain separate acceptance work.
