# Opt-in notification email

Migrations 0073–0074 add recipient/organization preferences and a durable notification delivery queue. Apply migrations before starting the updated web and worker. Existing users default to email disabled. The Notifications page lets each verified user enable or disable their own subscription for the selected organization. An unconfigured SMTP channel is explicitly shown as CONFIGURATION_REQUIRED; saving a subscription does not claim mail is currently deliverable.

`GET /organizations/{tenant}/notifications/preferences` returns the caller's preference, revision and configuration status. `PUT` accepts only `{emailEnabled, revision}`. The initial revision is null. Mutations require exact Origin, a current authenticated membership, shared mutation throttling and a matching revision. Enabling also requires a verified email. Concurrent edits conflict rather than silently overwriting another change. Audit records contain the enabled flag only. Preferences and retained delivery metadata are included in the password-confirmed account export without email bodies, recipient identifiers or lease tokens.

The worker projects at most 100 new notifications per batch into a queue, keyed uniquely by notification. Only notifications created after the current opt-in timestamp are eligible; re-enabling does not resend history. Each delivery records the preference revision. Current subscription, revision, verified/non-disabled account, membership and audience role are rechecked during claim and immediately before SMTP submission. Pending work from a previous subscription revision is canceled, including after a quick disable/re-enable. Membership removal cascades preferences, notifications and delivery records.

The queue stores no recipient address or message content. A verified address is read from the account immediately before sending. Email contains a fixed event title, the configured product name and a link to the organization's notification page. It contains no generated material, payment details or provider error. Subscription management is available on that page after login. In-app read state is independent of email delivery.

Delivery uses the same real SMTP adapter as authentication mail, with distinct queue identity and stable Message-ID. Leases are 60 seconds; retries are bounded at eight with exponential backoff. Proven SMTP rejection before acceptance may retry. An unknown outcome or an expired submitted attempt enters immutable RECONCILIATION and records an audit event; there is no blind replay. A crash before submission can recover. Unconfigured transport leaves queued work pending. A configuration outage can therefore delay notices created after opt-in until the channel is restored.

A subscription change cannot recall an email already submitted to SMTP. A crash after recording submission but before contacting SMTP can require manual reconciliation. Operators should correlate the delivery UUID with `<UUID@contentos.local>` in provider logs, never reset terminal queue state. The UI does not offer resend of uncertain notification email; the in-app notification remains available.

Production verification requires configured SMTP and an authorized operator mailbox. Local adapter doubles and browser tests do not prove inbox delivery. Sending-rate controls beyond the serial worker cadence, retention policy, production-scale queue latency and Telegram notification delivery remain to be completed.

## Queue maintenance and operator review

The worker cancels up to 100 no-longer-eligible PENDING or unsubmitted SENDING rows per maintenance pass, using row locks with SKIP LOCKED. Maintenance runs even without SMTP configuration. Concurrent maintenance workers process disjoint batches; a backlog of withdrawn subscriptions therefore does not have to wait for one mail attempt per timer tick. Active eligible work is preserved. Submitted rows are never relabeled canceled: their outcome may already be external. Expired submitted leases retain the reconciliation path, even after opt-out.

Platform operators can inspect `notification_email` and `notification_email_reconciliation` in the existing admin panel. Both support organization filtering and bounded pagination; the second shows only uncertain deliveries. Projections expose IDs, status, attempt count, safe error code and timestamps, never addresses, bodies, preference revisions or lease tokens. Every read uses the dedicated current platform-operator permission and is audited. Tenant ownership grants no access. There is no replay action. Migration 0075 adds delivery-list/account-export indexes and a preference lookup index.

Admin pagination now anchors to the original database timestamp and ID of the cursor row, rather than the millisecond-rounded JavaScript timestamp. Existing cursor fields remain accepted. A deleted cursor row yields an empty continuation; refresh from the beginning in that case. This avoids skipped records sharing a timestamp with sub-millisecond precision, including delivery records.
