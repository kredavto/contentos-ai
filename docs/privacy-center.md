# Privacy Center and account deletion requests

`/privacy` is an authenticated account page. Its overview returns only the current enabled user's public account fields, active-session count, owned organizations and latest 20 deletion requests. It never returns password/token hashes, mail envelopes or another user's requests. Unverified users can read their own overview and revoke sessions, but must verify email before requesting account deletion.

The page links the selected organization's brand to the existing consent, social connection, avatar, generated-video and source-photo controls. Destination services still enforce membership, role and consent rules. Those existing media deletion processes retain their own leases, provider cleanup, retries and audit behavior. Privacy Center does not bypass their authorization or duplicate deletion logic. Revoke-all-sessions uses the existing auth endpoint and also signs out the current browser.

## Durable request intake — not completed account erasure

POST `/api/privacy/deletion` accepts only current password, explicit acknowledgement and an idempotency UUID. Existing session authentication, Origin checks, JSON limits, a shared mutation budget and a separate 15-per-15-minute account-deletion budget apply. The password is verified with the existing scrypt implementation and is never stored in the request or audit. The transaction locks the enabled, verified user and compares the current password hash against the verified proof, fencing concurrent reset/disable. Requests serialize under the same user lock.

Migration 0038 adds `account_deletion_requests`: user UUID, internal request/revision IDs, idempotency key, timestamps and REQUESTED/CANCELLED state. A partial unique index permits one active request per account. The same key returns its original result, including CANCELLED; another key while a request is active conflicts. No free-text reason or sensitive content is collected. The state check requires a cancellation timestamp, and a trigger protects identity and terminal state. The initial generated SQL/snapshot were reviewed and corrected before their first application.

POST `/api/privacy/deletion/cancel` accepts request UUID and revision. It locks the same account, rejects another user's request and stale active revisions, then atomically updates state/revision and writes an audit event. Repeated cancellation returns the terminal result without writing another audit. Replaying an old creation request never reopens a cancelled request. Each audit includes the acting user and request UUID without password, content or reasons.

Requests are visible in the separate platform operator console's `deletion_requests` projection, guarded by its deployment flag and current operator record. Ordinary organization owners cannot read other users' requests. The projection has bounded cursor pagination and exposes only request/user IDs, status and timestamps. It does not send email or automatically notify an external service.

**There is no account-erasure worker in this slice.** Sending a request preserves account access, memberships, organization content, sessions and provider resources. The UI says so before submission and after success; it never reports that data was deleted. Owners are shown links to team ownership management so shared organization data is not implicitly erased. No request can be marked completed through this implementation. Extended account export (consent, billing and operational history), private voice deletion, deletion of text/generated-content histories, organization ownership resolution, provider cleanup orchestration, financial/audit retention and final account pseudonymization/erasure remain outstanding. These must be implemented and verified before the overall privacy requirement is complete.

Tests use synthetic accounts and cover current-password/verification/acknowledgement checks, duplicate/concurrent requests, unchanged sessions/content after intake, password/disable fencing, cross-user cancellation denial, stale revisions, cancelled-request replay, operator-only queue visibility and no sensitive audit payload. Browser coverage includes links into the existing consent screen, CSRF denial, wrong-password handling, persistence after reload, cancellation, responsive layout and actual all-device session revocation.

## Basic account JSON export

POST `/api/privacy/export` accepts only the current password. Verified, enabled accounts are required; Origin, session, mutation and separate 15-per-15-minute export throttles apply. The password proof is rechecked under a user share lock inside a repeatable-read transaction with a five-second statement timeout. A concurrent password reset/disable cannot silently use an obsolete proof.

The versioned JSON includes an explicit scope and exclusion list: own profile, current membership IDs/roles/join dates, retained session creation/expiry dates and all deletion requests. It excludes session identifiers and credentials, organization materials/media, billing/consent records and operational logs. This is a basic account archive, not the completed full privacy export requirement. Data already removed from session storage cannot be reconstructed. No organization content or other member's data is selected.

Each collection allows at most 10,000 records and the compact archive at most 2 MiB; overflow fails with EXPORT_TOO_LARGE, without a truncated file or success audit. The operator-assisted large/extended export workflow remains to be implemented. Successful transactions audit ACCOUNT_DATA_EXPORTED without archive contents; this means prepared, not confirmed saved on the user's device. Repeated downloads are independently audited. Responses are no-store; the browser creates a JSON download, clears the password and revokes the temporary object URL. No persistent server export object or public download URL is created.
