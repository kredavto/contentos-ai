# B-roll from the private media library

Video Studio supports up to five optional, explicitly confirmed USER_MEDIA video inserts per render. Add/remove rows, select ready MP4 files from the same brand, and choose each start/end in the main video and the source excerpt's start. Intervals must be ordered and non-overlapping; adjacent intervals are supported. The UI uses seconds at 0.1-second increments; the API persists integer milliseconds. Changing an asset or timing clears that row's checkbox. Other confirmations are preserved, and the default is no inserts.

Each insert replaces the whole picture using the selected crop/contain mode. Insert audio is muted; the main voice and optional background music continue. Captions and the watermark are applied once after all overlays, so they remain visible over every insert. The main timeline and duration do not change. Between intervals the original picture returns; short source clips are rejected, never silently looped or held until an interval ends. Optional intro/outro surround the composed main part without changing its stored B-roll timing.

Optional symmetric fades blend an insert with the main picture at both edges. `fadeMs` is an integer from 100 to 2,000 milliseconds per edge, and twice its value must fit inside the insert. Omit the field for hard cuts; API zero is rejected rather than normalized, preserving the identity of older requests without the field. The UI defaults to hard cuts and clears confirmation when fade settings change. At the shared boundary of adjacent faded inserts, the main picture is visible: this is not a direct crossfade between the two source clips. Fades do not extend intervals, overlap them or shift captions, sound or bookends. Timing is resolved to the 30 fps frame grid.

## Contract and persistence

The video creation endpoint accepts optional `brollClips: [{assetId, startMs, endMs, sourceStartMs, approved: true}, ...]` with 1-5 entries. Legacy `broll: {...}` remains supported, with its previous request identity; supplying both forms is rejected. No inserts means omitting both fields, not an empty array. Each interval must last at least 100 ms, remain within the maximum 180-second main-video bounds and the reserved duration minus intro/outro, and fit the selected asset. The worker checks the actual video stream durations too. If the generated main video is shorter than any requested interval, the task fails without capturing its video reservation; it does not silently move or shorten an insert. Actual remote provider costs remain separate from that reservation.

Migration 0052 created `broll_segments`; additive migration 0054 adds `position` with default 0 for existing rows and replaces the single-project uniqueness constraint with tenant/project/position uniqueness. Position is constrained to 0-4, limiting each project to five rows. Composite tenant foreign keys, USER_MEDIA/null-prompt/approval and per-row timing constraints remain. Ordered non-overlapping intervals and all source assets are checked before reservation and again by the worker under the tenant lock. Selection is fixed for a render and part of request idempotency; changes require a new request. Project listing retrieves the ordered collection separately so joins cannot duplicate projects or distort the 50-project limit. Public `brollClips` contains asset IDs, timing and approval, never storage keys; the legacy `broll` projection is populated only for a single clip.

Additive migration 0055 stores `fade_ms` with default 0 for old hard-cut rows, checks its allowed range and requires both fades to fit the segment. Public projections omit zero and include the configured positive value. Fade settings are part of request idempotency and survive caption review, retry and source-readiness checks. They do not affect the reservation or actual-duration billing.

## Access and lifecycle

Creation validates current writer role, same-brand ready video, storage configuration, source duration and timing before reservation. Execution rechecks membership, approved script, current avatar consent and media state before provider work, reads, final writes and completion. A missing or deleted source blocks pending work, including a deletion racing with a read or final write. Terminal failure releases the reservation exactly once. Existing remote uncertainty/reconciliation rules remain in force.

All selections survive subtitle review and local retries without another paid avatar submission. A task waiting for subtitle review remains blocked if any source is deleted; a writer can delete the unfinished video to release the reservation. Completed videos own their composed bytes and remain usable after source deletion, while their existing avatar/voice consent rules still apply. Video deletion removes all B-roll rows during cleanup. Adding more inserts does not add video seconds: the existing actual-duration charge applies.

## Processing boundary and verification

The core resolves tenant-owned metadata and reads exact bounded bytes through the storage provider. Each source is bounded by the library's 64 MiB limit, and the selected B-roll inputs together are capped at 256 MiB (repeated selections count separately). The aggregate is checked before reservation and independently at the processing boundary. FFmpeg receives no caller paths, URLs or filter expressions. It probes each normalized MP4: one H.264/YUV420P video stream at 30 fps and at most one audio stream, dimensions at most 1920 per axis. Silent clips are supported. The video stream duration, rather than a longer audio tail, bounds each excerpt.

Generated private filenames, forced MOV demuxer, disabled external references, restricted protocols, minimal subprocess environment, bounded output and timeouts are retained. Temporary files are removed on success/failure. The [official FFmpeg overlay documentation](https://www.ffmpeg.org/ffmpeg-filters.html#overlay) informed the timestamp/EOF handling. Real FFmpeg tests inspect frame colors before/during/after the interval, source offset, captions/watermark above the insert, and audio frequencies to prove that main voice/music persist while insert audio does not.

For fades, the adapter trims the source, resets its local timestamps, scales it, adds an alpha channel and applies `fade` to alpha only. It then shifts timestamps into the main timeline and overlays the result. Captions/watermark are applied afterwards, so their opacity is unaffected. Installed FFmpeg 5.1.9 filter help was checked for alpha fading. Real tests inspect mixed source/main colors during entry/exit, fully opaque frames, adjacent boundaries, sound frequencies and the final duration with intro/outro.

## Remaining scope

Editing a selection after job creation, direct clip-to-clip crossfades, asymmetric transitions, AI_IMAGE/AI_VIDEO/STOCK sources and stock licensing are not part of this slice. Optional [intro/outro](video-bookends.md) surround the main video; B-roll timing still starts at the beginning of the main part. Live storage/provider verification and production deployment remain outstanding.

Deploy matching web and worker versions before accepting multi-clip/fade requests: older workers may understand only one segment or ignore fade settings. Database defaults preserve existing hard-cut rows at position 0; they do not add rendering capabilities to older workers.
