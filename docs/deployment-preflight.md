# Offline deployment configuration preflight

Run `pnpm config:check --role web` or `pnpm config:check --role worker` with environment injected by your secret manager. This command does **not** load `.env`, create keys, write files, connect to any service, spawn a process or execute FFmpeg. Do not paste secrets into command arguments or share environment dumps.

The fixed production core/auth/storage profile requires `NODE_ENV=production`, HTTPS origin `APP_URL`, PostgreSQL `DATABASE_URL`, native Redis `REDIS_URL`, SMTP `SMTP_URL`, bare-email `EMAIL_FROM`, `CREDENTIAL_ENCRYPTION_KEYS`, `CREDENTIAL_ACTIVE_KEY_ID`, `STORAGE_PROVIDER=s3` and `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`. Both roles need auth email configuration: the web creates the encrypted outbox and the worker delivers it. The worker profile additionally requires absolute `FFMPEG_PATH` and `FFPROBE_PATH` paths (including library/video/cover processing prerequisites), even if current feature flags are disabled.

The SMTP adapter’s existing pure URL configuration parser is shared with this command, including its option allowlist; no mail transport is constructed. This stricter production preflight additionally rejects explicit `ignoreTLS=true` and `tls.rejectUnauthorized=false`, without changing the runtime adapter. The existing runtime environment parser and credential-vault constructor are reused without changing runtime behavior. The constructor validates keyring shape, canonical 32-byte base64 keys and active-key membership; it does not encrypt or generate keys. Keep existing keys for stored credentials/outbox; this command is not a rotation procedure.

S3 validation is deliberately **conservative shape checking**, not full provider validation: nonblank required strings, the current adapter bucket-name pattern, HTTPS origin-only custom endpoint, runtime enum checks and a KMS key when `S3_ENCRYPTION=aws:kms`. A KMS key with another encryption selection is rejected. No SDK/provider is constructed. Valid-looking regions, buckets, credentials and keys may still be unusable. The database and Redis checks validate URL scheme/host, not connection parameters or access. EMAIL_FROM must be a bare address, not a display-name form.

One JSON report goes to stdout with fixed group/key identifiers and status codes only. No supplied values, URLs, active key IDs, raw parser errors or stacks are emitted. `configured` means locally accepted shape, never credential verification. `worker_binaries: disabled` in the web report means that worker-only check was not selected, not that deployed workers are disabled.

Exit codes: **0** offline-valid for this profile; **1** invalid/missing configuration or safe internal failure; **2** incorrect arguments. Exactly `--role web` or `--role worker` is accepted. This intentionally does not offer a partial-success development profile.

**Not operational readiness:** connectivity, credentials, applied migrations, SMTP delivery, S3 permissions/writes, binary execution, worker health, live AI/social/payment integrations and backups remain unchecked, explicitly listed in every normal report. Provider-specific acceptance is outside this profile even when flags are enabled. Run migrations once through the approved deployment procedure, then the existing deployment smoke/readiness checks and authorized live acceptance tests. A zero exit code must never be used as proof of production readiness. See [deployment](../DEPLOYMENT.md), [environment](../ENVIRONMENT.md), and [container operations](../deploy/README.md).
